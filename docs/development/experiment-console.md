# 実施者のPCから実験を進める

被験者はコントローラー、メニュー、文字入力、開始・終了・保存を操作しない。実施者がこのUbuntu PCのブラウザーを使い、ゴーグルが計測・FB・保存を実行する。[操作の分担と進行仕様](../specifications/operation-flow.md)

ソフトウェアの動作確認と、実機・現地での受入れは別である。[残作業と確認証拠](remaining-work.md)を見てから機器を使用する。

## 最初に準備する

1. [ReleasesからAPKを導入](android-build.md#releasesからインストールする)する。Windowsの共用PCはAPKのダウンロード・USBコピーに使えばよい。
2. 実施者用Ubuntu PCにはNode.js 24を事前に準備する。このリポジトリを使う場合は既存のmise・just環境を使う。会場でパッケージをダウンロードしない。
3. [PCのホットスポット](field-network.md)を有効にし、Focus Visionを接続する。インターネット接続の表示とLANの疎通を混同しない。
4. PCで次を実行する。ホットスポットを後から有効にした場合は、コマンドを終了して起動し直す。

```sh
just experiment-console
```

ブラウザーで **http://127.0.0.1:8765/** を開く。コマンドはWi-Fi設定を変更しない。PCにはUnity・VIVE Hubを常駐させず、画面共有や動画ストリーミングも使わない。

Releaseの`operator-console.zip`を使う場合は展開先で`sh start.sh`を実行する。同じReleaseのAPKと組み合わせる。これは実施者用Ubuntu PCの起動手順であり、Windowsの共用PCへ開発環境を入れる必要はない。

5. ゴーグルを被験者へ渡す前に起動する。ゴーグルに表示された6桁の番号をPCへ入力し、対象のゴーグルを承認する。番号は接続確認用で、参加者IDではない。
6. 起動ごとの接続先・実行環境を確認する。PCのスリープを止め、電源を確保し、PCを走路の外へ置く。接続確認は実施者が済ませる。

## 普段使う画面

| ページ | 実施者が行うこと |
|---|---|
| 実験進行 | 現在の課題、次の説明、追跡・校正・保存・通信を確認し、主ボタンで開始または終了を確認する |
| 実施前設定 | 来訪、主要側、音量、入力方式、5台の役割と校正を設定する |
| 記録・例外対応 | ZIP回収、USB用書出し、停止確認、原因対応、規定の再試行・欠測・来訪中止を行う |

群は割付前に開示しない。来訪作成時の「登録順」は理解確認のモダリティ順に使うので、IDの数字と別に正しく登録する。個人名は入力しない。

## 被験者を迎える前

- 実機入力を選び、5台を1台ずつ動かして識別する。[取付・校正](tracker-measurement.md)に従う。
- 車体・左右車輪・コースを可能な範囲で実施前に校正する。新しい来訪では手首校正を取り直す。
- 停止中の機器確認では、音／表示／無提示を選んで3状態を試す。模擬提示であり、実際の手の動きを測定した結果ではない。
- 実機入力が取得できなくても合成入力へ自動で切り替わらない。合成入力は技術確認専用として明示的に選ぶ。画面と記録に入力方式を残す。

## 1回来訪の操作

1. 「実施前設定」で研究用ID番号と登録順から来訪を作成する。進行画面へ戻り、同意・適格性を確認する。
2. 装着・校正・視界・音量・保存を確認する。被験者は手を指定位置へ添えるだけで、収録・確定は実施者が行う。
3. 共通習熟、事前評価を順に進める。各開始前の10秒はPCに表示する。被験者へは口頭で開始を指示する。開始後に勝手に別の課題へ切り替わることはない。
4. 事前の基準量と目標を確認する。基準量不足では先へ進めない。正常計測でプッシュが少ないことだけを理由に追加走行しない。
5. 音と表示の理解確認を行う。被験者の口頭回答について、状態と次のこぎ方を入力する。模擬提示は規定の順序・時間で実行される。必要な再説明・再確認も規定内で行う。
6. 理解確認成立後、割付表を開示して群を登録する。以後は群・主要側・目標を変更しない。
7. プログラムが選ぶ課題・反復に従って開始する。訓練2分が終わったら、新しい走行・周回を始めず、安全に終えるよう口頭で指示する。FB終了後も安全停止まで記録を続ける。
8. 安全に停止し、動画の保存を確認して終了する。単に静止したことだけで8の字の正しい完了とは判定しない。正式な時間とエラーは動画で採点する。
9. 直後評価・質問紙の後に休憩開始を確認する。20分を短縮して保持評価へ進む操作はない。質問紙が時間内に収まらない場合は、理由を残して省略する。
10. 保持評価、取り外し、体調と記録の確認を行い、ZIPを回収する。

手順と予定量は[実験手順](../experiment-protocol.md#90分の進行)が基準である。準備、位置戻し、安全停止、再試行に要した実時間も記録する。ソフトの合成入力試験だけで、実際の被験者が90分で完遂できると判断しない。

## 中断したら

「中止・FB停止」は通常終了と別で、未完了として閉じる。PC・ブラウザーとの通信が途絶したときも提示を止める。PCへ停止を任せきりにせず、実施者は口頭で安全停止を指示する。

1. 物理的に停止したことを確認する。追跡がない場合、ボタンを押しても追跡・校正が修復されるわけではない。
2. 記録・例外対応で原因を確認し、必要なら停止後の理由を確定する。安全中止や時刻不成立を技術的な理由へ変えて再開しない。機器・保存・校正を直す。設定変更は停止中に行う。
3. 停止・原因対応を確認する。再接続だけでは試行を再開しない。
4. 技術的不成立だけ、規定上限内の再試行を選べる。それ以外は欠測として次へ進むか来訪を中止する。安全中止・参加者の中止希望では続行しない。

アプリ再起動では「直近の未終了来訪を復元」する。基準値・群・試行履歴を読み戻し、校正と物理的な停止を確認する。保存済み質問紙がある場合は新しい回答で上書きせず、元の回答を照合して進める。中断した休憩の成立は外部記録と照合し、確認できないまま保持評価へ進まない。終了済み記録と来訪状態のずれを検出した場合は自動で再試行せず、保存記録と動画を確認する。

## 実機なしで練習する

```sh
just experiment-console-demo
```

確認番号は`123456`。これは**操作画面のデモ**で、正規の実験順序や測定性能の試験ではない。正規の進行処理はUnityのテストと`just experiment-soak`で確認する。[画面画像](xr-preview.md)
