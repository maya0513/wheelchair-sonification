# ログの保存と実出力時刻の測定

ログを保存し、入力・処理・実出力の時間関係を確認するための開発資料。研究として残す項目は[記録様式](../operations/record-forms.md)、性能の受入れ基準は[検証計画](../specifications/validation.md)を参照する。

## 後から原因を追えるログを残す

**ログ**は何が起きたかの時刻付き記録。開発者向けの`Debug.Log`だけに頼らず、解析で読み直せるCSV等として保存するのが推奨。CSVは列名・単位・欠測表現を固定し、メモ等のカンマや改行を適切に扱う。

| 記録の層 | 必要な内容の例 |
|---|---|
| セッション | 研究用ID、群、課題、試行、機器ID、校正、設定の控え、ビルドとGitコミット |
| 取得入力 | 位置姿勢、座標系・単位、追跡状態、SDKから得られる元の時刻と意味、受信時刻 |
| 計算 | プッシュ開始・終了、推定角度、3状態、有効／無効、除外理由 |
| 提示 | 提示依頼・予約・取消・打切り・終了、対象イベント、予定長とソフト側で把握した長さ |
| 運用 | 接続断、校正やり直し、保存異常、停止・再開、未完了理由 |

時間差には**単調増加する時計**（通常、途中で時刻合わせの影響を受けず進む時計）を使い、暦の時刻は別に残す。SDK、PC、音声、動画が別の時計なら、同期の対応点と誤差を記録する。SDKが元の測定時刻を返さない場合は「取得不可」とし、Unityが読んだ時刻をセンサー測定時刻と呼ばない。

記録再生には「入力、元の時刻列、校正、設定、処理に使ったGitコミット」を揃える。合成データを使う**デモモード**と実測を明示的に区別し、実験時に模擬入力へ自動で切り替えない。実施者用の診断画面は参加者用表示と分け、参加者に角度数値等の追加FBが見えないようにする。

保存は試行終了時だけに全てをまとめず、処理を妨げないバッファと定期的な書出しを検討する。未書出し分は異常終了で失われうるので、書出し頻度と欠落を試験する。強制終了時の保存を保証したと書かず、保存済みファイルと未完了試行が識別できるようにする。試行ごとに別の識別子を付け、再起動で上書きしない。

現在の[模擬入力版](feedback-demo.md#記録を確認する)では、設定JSON、イベントCSV、正常終了の印をセッションごとに保存する。入力は手動の接触イベントと既知角度であり、実測位置姿勢やセンサー時刻ではない。具体的なファイル・列・未完了の扱いは同資料で管理する。

実測版のファイル、位置姿勢の欠測表現、端末からの取り出し、再解析は[実測記録](research-records.md)にまとめる。実測判定では1フレーム分を処理する間、時計をその取得時刻に固定して再現性を確保する。この時刻は各APIが実際に呼ばれた瞬間や光・音の発生時刻ではない。実出力の検証は以下の方法で別に行う。

## 音と表示の実出力を測る

Unityの`AudioSettings.dspTime`は音声システムの処理サンプルに基づく時刻で、`AudioSource.PlayScheduled`はその時刻上で再生を予約する機能。[音声時計][U9] [再生予約][U10] これらは**スピーカーから実際に音が出た時刻の測定器ではない**。予約の余裕時間を増やせば遅延も増えるため、使うだけで低遅延になるとは扱わない。

本研究への推奨は、3音を事前に用意して読み込み、プッシュごとのファイル読込や重い音生成を避けること。音ファイルの周波数・長さ・フェードを確認し、機器からの実出力も別に測る。視覚の300 msもフレーム単位になるため、指定値と実測値を区別する。

| 測る区間 | 方法の候補 | 注意点 |
|---|---|---|
| 入力受信→判定→提示依頼 | 同じ時計によるログ | センサー側の遅れ、描画・音声出力待ちは含まれない |
| 判定→画面／音の実出力 | 判定時に出す検証用マーカーと実表示・録音を同期して比較 | 判定マーカー自身の出力遅延も評価する。アプリログだけで断定しない |
| 動画上の離手→画面／音の実出力 | 手と表示を撮影し、音も共通の収録系で記録 | 映像・音声の同期、遮蔽、フレーム間隔を確認 |
| 実出力開始→次接触開始 | 次の接触までを同じ収録系で確認 | 新規開始が回復期か、開始済み提示が次プッシュへ続いたかを区別。判定不能は成功と数えない |

例えば60 fpsの動画は1フレーム約16.7 ms、120 fpsなら約8.3 ms。ただし高フレームレート動画で音声が取れるか、映像・音声にずれがないかは機器で確認する。PCの画面収録だけではHMDの実表示を測れない。利用可能な範囲では高速度撮影や音声録音を使い、さらに精密な測定が必要ならフォトダイオード等を検討する。新規購入は本資料の前提にしない。測定の分解能・同期誤差が目標に足りなければ「確認できていない」と記す。

## 検証結果の照合

合成入力で計算が正しいことと、実際の動作を正しく推定できることを分けて確認する。イベント検出、角度、状態別精度、追跡、提示の数値基準は[検証計画](../specifications/validation.md#機器の受入れ基準)に従う。全方向、加減速、姿勢差、再装着を確認し、少数の成功例だけで本計測へ進めない。
